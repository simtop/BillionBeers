# Distinctive design directions

Use this reference when the user asks for original, expressive, app-inspired, or fused designs.

## Learn from the actual evidence

Compare earlier outputs at the level of decisions: hierarchy, product art, metadata, actions, rhythm, and density. Separate a skill's advice from the model's interpretation and the resulting implementation. A previous failed mix may have combined the wrong decisions; it does not establish that synthesis is inherently worse. Prefer the user's latest reactions over an earlier recommendation.

Build a short design brief with a desired character and concrete constraints. For example, a beer discovery app might feel like a collectible field guide: confident titles, deliberate bottle presentation, warm accents, and readable technical data. This is an example, not a default theme for other products.

## Use app references precisely

Inspect a small number of relevant reference screens or first-party design accounts. Name the screen, source and date where available. Identify the transferable mechanism: distinctive type hierarchy, imagery-led discovery, progressive search, or a consistent accent. Explain how the proposal adapts that mechanism to this product. Do not claim to reproduce the current app from an old article, copy proprietary assets, or use popularity as usability evidence.

References should clarify a direction rather than turn every app into the same imitation. A bespoke typeface in another app can motivate a deliberate type hierarchy using the project's licensed fonts. Native navigation, semantics, touch targets and larger-text behavior still apply.

## Give alternatives different hypotheses

For an exploratory request, useful alternatives may include a focused refinement of the current identity, an expressive editorial direction, and an imagery-led direction. State the intended character before coding. Make distinctions visible in composition and hierarchy, not just accent colors. Do not add invented ratings, popularity, recommendations, inventory counts, or category data for decoration.

Render the same underlying content, art, states and viewport in all proposals. Additional art-quality evidence can be a separate comparison with real product images held constant across every option. Never improve only the proposed screen's fixtures.

## Curate a final synthesis

When requested, add a final rendered option after inspecting the preceding results. Trace each borrowed decision to its source proposal or earlier experiment. Resolve conflicts explicitly: large portraits versus list density, expressive headings versus header actions, restrained metadata versus meaningful status colors. Reject ideas that dilute the chosen identity or harm the primary task. A synthesis should be a coherent direction, not the union of every component.

Check both a browsing screen and a detail screen when available. Keep palette, title treatment, image language, and action hierarchy coherent; do not force the same layout on both. Include one meaningful cost or unresolved question in the conclusion, and distinguish visual judgment from tested interaction behavior.
